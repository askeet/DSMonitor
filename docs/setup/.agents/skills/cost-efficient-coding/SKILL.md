# Cost-efficient coding

Consider this skill for ordinary coding, debugging, refactoring, testing, and review, including natural-language requests to delegate that work; explicit `$cost-efficient-coding` also applies. Respect the user's and project's scope and restrictions. The user's selected primary model and effort remain the coordinator throughout; never change either silently. Honor an explicitly requested external provider; do not substitute another provider or native implementation silently. Optimize for regression-safe completion, accounting for native and external usage, coordination, retries, and rework. Keep trivial work direct when delegation costs more than it helps, unless the user requested delegation; favor an authorized, capable external worker for substantial bounded implementation and tests when beneficial. The coordinator defines scope and acceptance, integrates evidence, arranges required QA, and makes final decisions. The worker implements, tests, and self-reviews within its assignment; an independent reviewer verifies when required.

## Permission and execution boundaries

Adding, updating, installing, downloading, or restoring project dependencies (NuGet, npm, pip, etc.) requires explicit user approval covering the task and permitted dependency scope, given in the task or separately. Approval to implement a feature alone does not grant it. Approval to add a dependency covers the necessary project-local download, installation, and restore steps for that approved addition within the user's limits. The coordinator must convey the approved scope to delegated workers. Reuse approval for necessary operations within that scope across commands and worker continuations without asking each time; for a dependency, version, or operation outside it, stop and request additional approval through the coordinator. Workers must not infer missing permission, bypass approval gates, or change Forge Delegate configuration or `autoApprove` to enable dependency installation. Existing dependencies and offline/no-restore builds or tests remain allowed without new installation approval.

**Native-first dependencies.** The coordinator handles trivial selection, compatibility, approved project-local installation and verification directly. Delegate bounded, edit-free research to authorized DeepSeek only when uncertainty or risk justifies it, subject to existing gates; review findings, obtain missing consent, install and verify, then delegate in-scope implementation. If DeepSeek discovers an unapproved dependency, return `BLOCKED` with justification for coordinator review.

The primary and every native or external worker need separate explicit user approval for system-wide installations of software or packages; SDK, tool, plugin, or extension installations or changes; changes to OS or security settings, filesystem permissions, Developer Mode, environment variables or system configuration; and any request for or use of administrator/elevated privileges. Project dependency approval does not cover these operations or carry forward as blanket permission for later tasks. Never bypass these restrictions through agents, scripts, subprocesses, package managers, other tools or environments. Before requesting missing approval, explain the operation, necessity, system effects and any nonprivileged/noninstalling alternative; stop until approved. Read-only inspection and source analysis remain allowed. Ensure build and test commands do not trigger unapproved downloads or changes; use existing dependencies and no-restore/offline options when appropriate, and report missing-dependency blockers. Include these restrictions and the approved dependency scope in every delegated task, even if the worker may not load this skill.

Project delegation authorization and feature-implementation approval alone do not grant access to secrets, credentials, private runtime data, unrelated repositories, or unapproved external sharing; nor do they authorize destructive operations, commits, dependency, system, security or sandbox changes. Apply the specific approval rules above, obey platform gates, and never enable automatic approval silently. A sandboxed CLI failure does not prove the external path unavailable, but evidence reuse never permits sandbox bypass, expanded writable roots, elevation or unauthorized unsandboxed execution. If the actual external child hits a permission or execution restriction, stop and report it; past success does not imply unrestricted access.

If interactive approval is unavailable, stop and report `BLOCKED`; do not repeatedly retry, change permissions or enable auto-approval. For a suspected hang or timeout, use supported status and, if available and appropriate, cancellation; verify termination. If unavailable or unverified, report the last observed state and retain ownership without overlapping work. A timeout alone proves neither the cause nor termination.

## Route by risk and establish the architecture

Classify before substantial implementation and reassess after tests: **low** is isolated, reversible and clear; **medium** has interacting components, compatibility or moderate regression exposure; **high** has material persistence/migration, data integrity or security risk, or uncertain system-wide impact. A routine query or mere mention of SQLite, filesystem or security is insufficient for a high gate. Limit exploration to the relevant context; keep classification internal unless useful. Low-risk isolated fixes need no architecture agent. Medium work normally uses the external worker and the QA triggers below. Genuinely difficult high-risk work requires a read-only native senior architecture gate before implementation, including transactional atomicity, migrations, crash recovery, security-sensitive file identity, permission boundaries, irreversible data changes and repeated critical defects. Reuse sufficient prior evidence; investigate again only for a concrete gap. Reserve senior arbitration for unresolved critical decisions.

Require the bounded delegated pre-implementation audit for high-risk work, including untrusted input/parsing, security, persistence, concurrency/async, identity/ownership/authorization, complex contract changes, or repeated defects/QA failures. A simple isolated low-risk task skips this separate audit. For audited work, use this order: audit; coordinator assessment and finite acceptance matrix; required native architecture decision where the high gate applies; one consolidated authorized implementation; independent final QA. An external worker may investigate high-risk issues but may not implement security-sensitive, data-integrity-sensitive or destructive changes until the native decision, explicit safe plan and authorization are complete. Keep investigation read-only apart from authorized disposable probes in isolated storage. Preserve a reliable source baseline, prohibit other edits, inspect unexpected changes afterward, and do not mistake instructions for filesystem isolation. Reproduce known defects when practical with synthetic tests/probes; inspect relevant code, tests, adjacent failure modes, valid counterparts and root causes. Return paths, evidence, limitations and a finite risk/acceptance matrix. If the audit cannot run safely or readiness is unreliable, report the blocker; never silently skip it or substitute unauthorized work.

The coordinator independently evaluates audit evidence against the affected contract, combines supported findings by root cause, rejects unrelated/unsupported claims, and defines finite positive, negative, boundary, cross-component and compatibility cases. Report missing evidence without repeating the whole audit. Give the independent senior reviewer a self-contained architecture and implementation coordination assignment under established authorization. The reviewer's architecture work is read-only: inspect relevant sources, tests, requirements, failures and prior findings; run only authorized non-mutating diagnostics; identify root cause, risk, correctness/security invariants, trust boundaries and threat model, minimal strategy and adversarial tests. No source, test, documentation, dependency or configuration edits; no project file creation/deletion, refactoring, destructive actions, installations or unauthorized elevation. Stop when evidence suffices. Record and compare source baseline/fingerprints around review; preserve user work and inspect changes before implementation.

Before production delegation, record a compact decision of `APPROVED FOR IMPLEMENTATION`, `CHANGES REQUIRED` or `INCONCLUSIVE`, with existing contracts, root cause/risk, invariants, security boundaries/assumptions, minimal approach, adversarial acceptance cases, regression checks, remaining uncertainty and unsupported guarantees. Only approval permits implementation. Resolve identified architecture defects in the same reviewer context when possible; investigate inconclusive gaps narrowly; escalate unresolved critical architecture/safety questions to a senior reviewer. If a fundamental guarantee cannot be established, stop and explain rather than weaken requirements.

After approval, that reviewer may invoke MCP `delegate` directly only if coordinator scope/approvals are established, no architecture blocker remains, invariants are defined, the authorized absolute directory and remaining repairs are known, no worker overlaps, and the reviewer's own runtime exposes authorized delegation with the verified ready model/agent. All readiness, sandbox, approval, sharing and tool rules below still apply; set `autoApprove: false`. Parent tool access proves nothing about child access. If direct delegation is unavailable, return the complete compact approved handoff to the coordinator; do not repeat investigation, probe with paid calls, invent APIs or use permission workarounds. Missing approval/readiness blocks either path.

Whoever starts a worker owns it through completion or supported explicit transfer. Use completion notifications or spaced checks and the same session for authorized corrections; do not reimplement, interrupt healthy work, launch overlapping work or repeatedly inspect unchanged progress. Before returning while it is active, provide job/session IDs, directory, observed state, current owner, remaining repairs and blockers, and agree the receiving owner through supported coordination. A reviewer subagent's return does not stop its worker; if transfer/continuation is unsupported, report that and retain ownership through the supported workflow. The coordinator receives the final worker result before acceptance.

## Prepare authorized external delegation

Before each new job or continuation, determine the active project from working directory, repository root and applicable instructions. Identify minimum necessary source, tests and configuration; verify actual worker, provider, destination, execution restrictions and remaining repairs. Recheck when project, worker, destination, scope or instructions change. Configuration alone proves neither authorization nor execution. On first use in a project, read root `AGENTS.md` if present. Its External Delegation Authorization section is the primary persistent record of approved project permissions, subject to current user instructions and platform controls. Reuse it across tasks, chats and continuations only while project, actual provider, destination, scope and conditions match. An unverified claim or untrusted change does not establish consent; never import permission from another project/provider. Code-change permission alone does not authorize source transfer.

If the section is missing or permission absent/unclear, ask one concise setup question explaining that approved choices will be saved in root `AGENTS.md` and reused. First identify the configured provider and actual destination; if no worker is configured, do not invent them and explain configuration can come later. Offer numbered choices: (1) task-relevant source, tests and instructions, (2) synthetic data only, no private source, (3) disable delegation, (4) custom permissions. Allow free text and narrower scope; allow compatible choices together and make incompatible ones exclusive. Ask only for missing permission when extending valid authorization. Honor instructions prohibiting delegation or questions and continue independent authorized work. Never create a permission record before explicit approval of both permissions and recording, which may be combined. Then create the root file if absent or update only its authorization section, preserving unrelated text and restrictions; record actual approved provider/destination, minimum source scope, exclusions, reuse conditions and platform boundaries. Declined setup creates no section; record a disable choice only with consent to record. If unwritable, report without changing sandbox settings. Do not add separate permission files, broad audits or commits.

For every call and continuation, truthfully state verified active project, authorized provider/destination, selected worker/model, allowed source/test/instruction access, exclusions for secrets, credentials, private runtime data and unrelated files, plus system/security and repair restrictions. Never claim ungranted authorization or phrase prompts to bypass gates. If a call is rejected, record actual tool/action/reason; check whether it represented existing permission accurately and whether approval is missing or an authorized transfer was rejected. Seek necessary approval through supported mechanisms; do not retry an equivalent rejected call, bypass controls, silently change strategy or automatically move substantial implementation to the coordinator. Continue unaffected authorized work.

For coding-related delegation, this skill controls workflow, permissions, risk, QA and acceptance regardless of activation order. Load [delegate-work](../delegate-work/SKILL.md) once per chat only when external delegation is needed and it is not already active; use it for Forge Delegate execution mechanics. If unavailable, report the material limitation rather than claiming it was loaded. Do not reinstall or reconfigure integrations, or expand access to enable delegation. Inspect accessible current configuration (such as `get_delegate_config`) for changes/conflicts/overrides before external use, reusing applicable prior inspection. Require reliable non-generative evidence of effective agent, provider, model, intended step limit and applicable authentication; explicit agent/model selection must match, and the actual external path must be authorized with no known restriction. New/unknown models or agents, relevant changes, stale/conflicting/unreliable evidence require fresh verification. For an established, user-authorized Forge chain, reuse sufficiently current, trustworthy non-generative evidence only when the execution chain, versions, relevant configuration, agent, model and provider remain consistent and no evidence conflicts. A Codex-only CLI failure does not by itself invalidate that evidence or establish a Forge failure. Stored credentials alone do not prove current provider authentication; report their status separately. A permission failure on the actual Forge/OpenCode execution path remains a blocker. A catalog/config entry does not prove authentication. Never make paid calls or launch a worker as a readiness probe; if readiness cannot be established, report the exact gap.

Use the supported delegation tool and verified configured worker; explicitly choose the authorized directory, worker and settings where supported. Verify step limits, timeout, continuation and approval settings; use background execution when appropriate, keep `autoApprove: false`, and never assume timeout stopped a worker. Preserve verified worker reasoning settings: step limits do not establish effort; change effort only when supported, justified and authorized, distinguishing resolved settings from runtime-verified requests. Keep stable instructions and append incremental corrections in the same session. Prefix caching is best-effort, session reuse does not guarantee hits, and compaction may alter the prefix; do not rewrite stable prefixes or compress automatically without evidence of benefit. If the worker is unavailable/fails, report the issue and a safe proposed fallback; never silently replace it with native implementation.

## One external development cycle

Before edits, preserve a reliable comparison baseline. Prefer Git while retaining all user changes, including uncommitted and untracked files. Without Git, keep exact snapshots or content-preserving backups of affected files in authorized storage; hashes/test counts alone are insufficient. Keep baseline content outside model context when practical and never overwrite user work. Reuse known workspace/test information. Send a proportionate plain-text handoff: Goal/acceptance, Contracts, Scope, Checks, Evidence. Include absolute authorized root/paths, compatibility, approval boundaries, exclusions, known commands and remaining repairs; preserve exact missing/null/empty/explicit-value and field/segment-override semantics when relevant. Send paths, not copied source, histories or unrelated logs. For gated implementation, include the compact approved decision, invariants, unsupported guarantees, adversarial/error/compatibility cases, baseline/focused/regression/build/lint checks and final-diff review. Prohibit architecture changes; return to the gate if assumptions fail. Send the decision, not its full discussion.

Assign one consolidated implementation covering the agreed audit matrix when present. The worker must:

1. Inspect relevant code/tests/logs, reproduce practical defects, identify coverage gaps/root causes and baseline existing failures when feasible.
2. Implement agreed behavior and meaningful requirement-based tests for normal, boundary, invalid/error and compatibility paths, using existing tools and dependencies or approved task-scoped project dependency changes. Preserve passing tests: do not delete, skip, disable or weaken them to pass; justify any modification by an intentional requirement change or demonstrated test defect, and seek approval before removal.
3. Run focused and broader relevant regression checks and applicable build/lint checks. Investigate failures and make routine corrections within the shared repair allowance below.
4. After required checks pass, perform a risk-based adversarial self-review of the entire affected subsystem against the invariant matrix, including adjacent in-scope defects, invalid/nullable states, ownership, conflicts, failure paths and interactions where tests could pass despite a broken contract. For high-risk persistence, security, financial, concurrency or schema work, challenge the underlying contracts directly. Add meaningful negative/regression tests for gaps; reproduce confirmed defects when practical. While the assignment is active, fix confirmed in-scope defects within scope and remaining repairs without separate approval for each correction. Count applicable focused repair cycles against the shared allowance, consolidate failures, rerun affected tests, the complete invariant matrix, relevant regression suite and build checks. Repeat focused review only for new risk; do not enter an unbounded loop. Escalate changes to architecture, intentional contracts or authorized scope; do not make unrelated refactors, unapproved new dependencies, system changes or another phase. Review final diff, test preservation, unrelated changes and remaining risks.
5. Return `COMPLETED`, `INCOMPLETE` or `BLOCKED`; changed paths/behavior, acceptance coverage, extra risks investigated and defects found/fixed, new tests, baseline/focused/regression/build commands and results with exit statuses and counts, every existing test edit with justification, failures/repairs/remaining allowance, gaps/blockers, and available usage with provenance. Omit source dumps, but never failures or limitations. Passing tests alone is not completion or exhaustive verification.

Allow this cycle to finish without intermediate native handoffs unless a decision, approval or safety boundary requires one. For investigation-only work, prohibit project edits and compare against baseline afterward; permit only authorized isolated disposable probes. Before independent QA, the coordinator checks self-review evidence. If confirmed in-scope defects remain, seek correction in the active assignment or the one permitted pre-QA continuation below; then report `CHANGES REQUIRED` for unresolved blockers, exact blocked status for a blocked worker, or proceed to required independent QA. Missing evidence is not completion. Worker self-review is preliminary, never independent QA.

For asynchronous jobs, prefer completion notifications or awaited results. While active, call `check_delegation` every ~3 minutes; check earlier only when start response requires confirmation or there is a concrete user request, indicated failure, observed step-limit or approaching deadline. On `RUNNING`, inspect status only; avoid unnecessary output analysis. Retrieve completed/failed results promptly. Report unsupported periodic checks rather than invent scheduling. Use authorized passive logs when accessible. Avoid busy waiting, filler commands, unchanged status reports, usage-changing diagnostics/session exports, overlapping workers, partial-diff rereads and checks without reason. Batch independent checks, reuse valid evidence, and preserve timeouts, step limits, approvals and QA.

## Independent QA and acceptance

High-risk tasks and any of these triggers require a capable independent reviewer even when tests pass: (1) affected persistence, saved user data, configuration schema, serialization or migration; (2) changed behavior across interdependent components/subsystems; (3) insufficient affected coverage, failing relevant regression or unverified backward compatibility; (4) the same problem remains after two focused worker repairs; (5) unclear root cause, conflicting results or insufficient confidence. These override lightweight QA and fallback preferences. A senior primary may review directly unless it owned gated architecture or implementation coordination; then use a separate independent final reviewer. Reuse a prior senior review only if it covers the same final code and required checks. Architecture approval and worker self-review never replace final QA. Escalate unresolved critical architecture, security or integrity questions to a suitable senior reviewer with supported effort appropriate to risk. Low-risk work without triggers needs no separate senior reviewer; do not spawn one merely to rerun passing low-risk tests or summarize another agent.

After gated implementation, confirm editing stopped and capture final state before assigning QA. Before a read-only senior reviewer starts, record Git status/diff and file fingerprints including affected uncommitted/untracked user files; without Git use the exact baseline above plus fingerprints. Give goal/acceptance, contracts, paths, actual diff, baseline/checks and risks, and prohibit source/test/configuration edits while allowing inspection and validation. Avoid concurrent implementation/review. Afterward compare source, tests, configuration and file inventories; distinguish generated artifacts from unexpected edits/new/deleted files, inspect discrepancies, preserve user changes and revalidate if code changed. Consider a disposable workspace/worktree only when it materially improves high-risk safety within authorization. Shared filesystem and independent context are not physical read-only isolation.

The independent reviewer must inspect the actual focused diff against baseline and scope; evaluate the whole affected subsystem against approved invariants and acceptance matrix, including correctness, errors, compatibility, meaningful new tests, test preservation and unrelated changes; investigate new material risks with reproducible evidence without needlessly repeating an adequate audit; independently run required focused and broader relevant regression checks; verify worker claims against code/output; and report findings, gaps, blockers and risks. Do not reduce validation to save tokens or call prior review exhaustive when later testable defects appear. For arbitration, isolate the decision, competing evidence, locations, reproductions and compatibility risks; label hypotheses and require concrete findings, independent checks and `APPROVED`, `CHANGES REQUIRED` or `INCONCLUSIVE`. Wait for the result. The primary evaluates independent evidence and owns acceptance; avoid repeating completed checks absent changed code, conflicting evidence or a concrete gap. If mandatory review cannot start, fails, is inconclusive or leaves required checks incomplete, preserve evidence, report `REQUIRES INDEPENDENT REVIEW` and recommend manual independent review. The coordinator cannot sign off instead. Final approval requires mandatory review and validation to pass without unresolved critical findings.

## Repair budgets, continuation and recovery

Allow at most **two focused repair cycles after initial implementation** in each applicable external-worker implementation task, counting cycles within a job and across continuations; honor smaller task limits. Before each remediation, combine all currently discoverable failures into one bounded evidenced defect report. Afterward rerun the complete invariant matrix and relevant regression suite; list unexecuted checks. Record failed checks, corrections and rerun results, including attempts with no usable output. Track observable external repair delegations separately from worker-reported internal cycles, reconcile without double-counting, and mark unverified counts as uncertain. State remaining allowance on continuations; do not reset it through sessions, agents, models, coordinators or repeat architecture review. New user-authorized budget is tracked separately. Never claim technical enforcement without tool evidence.

The configured worker step/time ceiling is distinct from repairs, and neither is a target. Finish when requirements/checks are complete; do not spend unused allowance on extra calls, repeated exploration or failing commands without changes or diagnostic reason. Runtime step allowance may reset on continuation because it submits new input, not because the global session is uncapped. Require incomplete-work reporting at either limit. Do not raise/bypass limits, invent parameters or change provider configuration to finish. On budget overrun, exhausted unsuccessful repairs or no meaningful progress, stop further repairs and report diagnostics; the coordinator escalates to the reviewer, and senior reviewers seek senior arbitration for critical issues as needed.

If a returned worker reports confirmed in-scope self-review defects, the coordinator may request **at most one** focused same-session pre-QA continuation only when task policy explicitly permits it, no single-delegation restriction applies, repairs remain, and architecture, scope, unrelated functionality, dependencies, system/security settings, user decisions or execution/cost/repair limits will not change or be exceeded. Send the complete unresolved list together. Require fixes, meaningful regressions, affected tests, full invariant matrix, relevant regression/build checks, renewed focused self-review and remaining-risk report. Do not restart implementation or create another worker. If disallowed/exhausted, stop and seek separate authorization.

If independent QA finds a correctable defect and repairs remain, send one focused correction to the original session when supported, then revalidate affected behavior and repeat required independent final QA. Once exhausted, stop corrections, report defects/evidence, and get explicit user approval for additional bounded remediation, including QA defects, with defined scope, limit and acceptance checks. The prior allowance stays exhausted; risk gates and independent final QA still apply to approved repairs.

## Native collaboration and reasoning

Use actual `collaboration.spawn_agent` with a unique `task_name`, verified `model`, explicit supported `reasoning_effort`, `fork_turns: "none"` and self-contained message when overriding. Model and effort overrides are independent. Omitted overrides inherit; `fork_turns: "all"` inherits both and disallows overrides. Independent context/model override does not change or lower primary effort. Choose supported model/effort by complexity and risk, preserve explicit user choices, and do not raise effort routinely or infer actual effort from defaults. Check `collaboration.list_agents` and runtime capacity rather than assuming fixed slots. Use `wait_agent` and delivered results with concise `send_message`/`followup_task` updates. These tools offer no portable compressed-history, hidden-reasoning or shared-KV handoff. Native agents share files: prevent concurrent conflicting edits, keep reviewed code stable and revalidate after corrections.

## Reporting and setup

Report routing reason, actual models/tools, external calls and repairs, independent findings versus worker claims, test evidence and risks. End **every completed task**, including no-delegation tasks, with a concise **AI Usage Statistics** table. Show primary/native/external model and effort only as runtime-verified when current evidence supports each; otherwise label user-selected settings `user-selected, not runtime-verified` with `Runtime verification: Not available`, or `Not available` if not selected. Application identity (such as Codex Desktop), defaults, catalogs and historical sessions do not verify current model/effort. Reuse available evidence without routine identity probes.

Show external calls, input/output/cache-hit/cache-miss tokens, external cost and provenance, and native usage/cost when exposed. Use `0` only when verified. For confirmed zero external calls, calls/input/output are `0`, cache hit/miss `N/A`, cost `$0`. Otherwise unexposed applicable metrics or unknown activity are `Not available`; use `N/A` only when inapplicable. Cached input is part of input, never additive. Report `External tokens (reported aggregate)` when provided, else `Not available`; identify provider versus wrapper-estimated source, per-job/per-session/cumulative/unknown scope and per-task verification. Do not infer input/output from aggregates, reuse unrelated counters, treat cumulative as per-task or double-count overlapping continuations. Reconcile comparable independent non-overlapping counters only; otherwise give latest relevant raw value/scope. Compute deltas only from comparable known baselines and savings only with trustworthy usage/prices. Distinguish confirmed billing from rate estimates; do not invent counts/cost/savings, infer quota savings from external prices or assume native agents free. Use only executed-tool data; never call APIs, spawn agents or search logs solely for usage statistics. Keep no-delegation reports compact.

For changed files, follow the statistics with one concise suggested Git commit message scoped to inspected changes; identify unrelated/uninspected changes rather than implying inclusion. Never commit without authorization. Skill setup/validation must not spawn agents or make paid model requests.
